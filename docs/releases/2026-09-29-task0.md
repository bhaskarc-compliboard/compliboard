`declared`, `confirmed`, `labels`, `keys`, `document`. The rule the commit was built under, and the
reason it is one commit rather than two: **no prompt gained anything it did not read before.** Each
caller asks for the parts it already read and renders them where it rendered the same fields, in the
same words —

|---|---|
| `lib/documentScan.ts` (the scan) | `company`, `confirmed`, `labels`, `keys`, `document` — **not `declared`**; the scan does not read `company_switches` and did not start |

| `app/api/chat/route.ts` | `company`, `declared`, folded in only behind `RESEARCH_FACTS_BLOCK`, which is unset on production |

Proved rather than asserted: `scanPrompt` rendered from `HEAD`'s file and from the working tree with
one identical context hashed to the same sha256, `IDENTICAL: true`.

**The defect it closed.** Fourteen of the staging fixture's sixteen switches are site-scoped across two
plants, and the gate's SELECT asked for neither `scope` nor `entity_id`. The block rendered **seven
pairs of bare contradictions** — `Employees at this site = 1` beside `= 6`, air permit tier `title_v`
beside `none`, generator category `lqg` beside `vsqg` — under a heading telling the model to treat them
as settled. `KnownFact` gains a site and `subjectOf()` is the one place that renders it.

**The Company information page, at `/company-information`**, 900 wide, with the confirmation queue as
its first group: at most five question lines, a document's facts asked together as one line with
**Confirm all N**, a key with two different values lifted out as its own line. The sidebar badge counts

**`/to-confirm` redirects with a 308** (`permanentRedirect`) rather than 404ing, because

still what answers a confirmation, from the page and from the report drawer both.

## 3. Migrations 055 and 056, and what their verify blocks do

| | |
|---|---|
| **055** `a_confirmed_fact_has_a_site_and_a_date` | `entity_id` and `as_of` on `company_facts` and on `fact_proposals`. The one-per-key uniqueness becomes **one per company, key and site** — a unique index with `NULLS NOT DISTINCT`, because a plain three-column unique would have accepted two company-wide rows for one key, which is the thing the old constraint existed to prevent, reintroduced by widening it. The foreign key is **composite**, `(company_id, entity_id) → entities (company_id, id)`, so a fact cannot point at another company's plant; that needed a new `entities_company_id_id_key`. **Its probe rows hang off two throwaway companies**, the second existing only to own a site the first must not reach, and both are deleted. |
| **056** `a_person_can_say_it_themselves` | `company_facts.basis` accepts `declared`. **`fact_proposals.basis` is deliberately NOT widened** — a person does not propose a fact to themselves — and the verify block asserts it still refuses. One throwaway company, deleted. |

**Neither touches a single existing row.** 055 adds two nullable columns and swaps a constraint for a
wider one; 056 widens a CHECK. There is no `UPDATE` of customer data in either, which is the axis
migration 054 was the exception on in the last release.

**Both verify blocks test their constraints by trying to break them** (§3.7 — a CHECK nobody has
tried to break is a comment) and read privileges back rather than trusting a grant list. 055's
assertions were additionally re-run as real writes through the service role, and the refusals came
back with their Postgres codes: `23505` for a second company-wide row and for two rows at one site,
`23503` for another company's site on both tables.

**Applied to production: the owner's, recorded as such.** This session could not read production's
migration history — the brief limited it to one SELECT (§7 d). `npm run preflight` printed **pending
exactly `055` and `056`**; `npm run db:migrate:prod` was run, the word `PRODUCTION` typed, and it
finished; types were regenerated from production and came back **unchanged**, which is what you would
expect since 056 changes no column and 055's two columns were already in
`lib/database.types.ts` from staging.

**One thing in this session's own reach supports it.** `/api/company-information` cannot answer at all
unless 055 is applied: `lib/companyContext.ts:249` selects
`key, value, basis, entity_id, as_of, source_document_id, source_proposal_id` from `company_facts`, and
three of those columns are 055's. The smoke test's first line is that the page loaded and showed
"4 facts settled". **That is evidence 055 is on production, not proof the procedure ran as described** —
the distinction is the point of marking it.

## 5. What changes for a person on production, the moment it deploys

- The sidebar's fifth item reads **Company information** instead of **To confirm**, in the same
  position, carrying the same badge. The badge now counts **question lines** rather than keys.
- **`/to-confirm` 308s** to the new page. Every batch email already sent still works.
- The page shows the settled record — declared switches with the question each answered, confirmed
  facts with their site, their as-of date and the document they came from — and the queue above it.
- **Nothing a model concluded on its own appears in the record.** Pending proposals are questions;
  only a confirmed one becomes a fact. That is what lets the page say *"Nothing here was guessed."*
- A confirmed fact can now be **corrected in place**, and the correction says so: `basis` becomes
  `declared`, the document link and the as-of date go, the line reads *"you corrected this"*, and the
  original reading survives in `fact_proposals` as the history.

**What does not change:** no prompt, no model, no switch default, no audit route, and no existing row
in any table.

## 7. What the smoke found

Three, all on the page, none in the data. Each is fixed in **commit 4**, and each was checked at the
line before it was fixed.

**a. Confirm shows no pointer and no hover state.** The four actions on the page — Confirm, Confirm
all, Not right, Edit — were given text colours and no `cursor` or hover rule. *Not right* on the old
To confirm page had `underline hover:text-gray-900`; the new page's buttons did not carry it
consistently.

**b. The sidebar badge does not move after an answer.** `components/AppLayout.tsx` reads the count
**once per pathname** — its own comment says so: *"Read once per page load. A live count would mean
polling every screen in the product for a number that changes when the person themselves changes it."*
Answering a question does not change the pathname, so nothing refetches. Fixed without polling: the
page dispatches one `window` event after any answer or edit, and AppLayout listens for it.

**c. A document read twice shows its own two readings as "two different answers."** The smoke saw
*"Yes, kept in the front office"* and *"Yes — an AED kept in the front office"*, both from the same
Emergency Action Plan, one per reading. **Only two different documents should be able to disagree.**
The cause is the withdraw rule in `lib/documentScan.ts` `saveScan`, which withdraws a pending proposal
only when the new reading is **silent** about its key; a key the new reading restates with different
words keeps both rows. Changed so that re-reading a document withdraws every pending proposal from its
earlier readings; a confirmed or rejected one is untouched.

**d. Production already holds pairs like these** — and this was the one production read this session
made, `SELECT` only, printed in the commit-4 report with its counts for staging and production.
