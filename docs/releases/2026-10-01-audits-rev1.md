## 2. Migrations — 058, 059, 060, and what each verify block proves

```
$ npm run preflight          # READ-ONLY. Prints both lists and derives the difference.
  INPUT 1 — supabase/migrations/*.sql on disk: 61
  INPUT 2 — supabase_migrations.schema_migrations on dsfwmafnphdlfogetsus, every row (58)

    058_the_audit_as_rows.sql

    060_a_recurring_date_need_not_have_a_day.sql
  DERIVED — INPUT 2 minus INPUT 1 (applied but absent from disk):
    (none)
  PENDING COUNT: 3
```

**Exactly three, and nothing applied to production is missing from disk.** 055, 056 and 057 — the
Documents follow-ups — are already on production; `docs/HANDOFF-CODE.md` said otherwise until this
preflight corrected it.

**None of the three touches an existing customer row, and none is destructive.** 058 and 059 create
tables and columns; 060 replaces one CHECK with a strictly looser one, so no row already in the table
can be made illegal by it. Each file's verify block runs inside the migration, creates **its own
throwaway company**, and aborts the migration if an assertion fails — which is why a migration that
appears in `schema_migrations` is a migration whose assertions held.

### 058 — the audit as rows

Creates `audit_runs`, `audit_sections`, `audit_findings`. What its verify block proves, by **trying
the write and requiring the refusal**:

- **A finding cannot cite another company's document, record or run.** Every finding is tied to its
  run, section, document and scan by **composite foreign keys on `(company_id, <id>)`**. The block
  creates a second company, gives it a document, and attempts a finding on company A citing company
  B's document; it requires `foreign_key_violation`. **RLS cannot catch this** — the writer is the
  service role and passes every policy — which is the whole reason the constraint is a key and not a
  rule in code.
- **A run names what it audited.** `audit_runs_kind_has_its_subject`: an agency run has an
  `agency_label` and no `template_document_id`, a template run the reverse. Both halves attempted.
- **The per-kind shape.** A `date` carries a date, a `contradiction` carries two sides and two values,
  an `expected` row carries `basis = 'expected'` and the word `nothing_on_file`. Each attempted
  half-built and required to fail.
- **Deleting a run takes its findings** and leaves the documents alone.
- **`authenticated` may read and update and may NOT insert**, and `anon` holds nothing. Attempted as
  both roles, and then **read back** with `has_table_privilege` rather than trusting the grant list —
  because a grant list describes what you added, not what the role holds, and this project carries
  default ACLs that hand `anon` and `authenticated` full DML on any new table in `public` before a
  single GRANT runs.

### 059 — the checklist is the question

Adds `audit_findings.template_line` / `template_text` and `audit_runs.template_lines` jsonb. Proves
the lines store and come back as the same count; that a template run still may not also claim an
agency; that an agency finding may leave both new columns null (the rule is the writer's, because a
CHECK cannot reach through to the run's kind); that deleting the run takes its findings **and leaves
the checklist document on file**; and re-reads every privilege, because adding a column is a chance to
widen one by accident.

### 060 — a recurring date need not have a day

Replaces one CHECK:

```sql
-- was:  kind <> 'date' or due_on is not null
-- now:  kind <> 'date' or due_on is not null or recurs is true
```

Proves the recurring undated row lands as kind `date` with a null day and no word; that a **one-off**
with no day is still refused; that `recurs` **null** — "the model did not say" — is **also** refused,
which is the clause the migration's comment is about and the difference between `recurs is true` and
`recurs is not false`; that dates with days are unaffected either way; and that the other two per-kind
CHECKs and 058's cross-tenant foreign key still refuse what they refused.

**Proved again against the applied schema, as a signed-in write rather than inside the migration**,
because `supabase db query` is read-only and `supabase db push` swallows the verify block's NOTICE:

```
✓ recurring + no day accepted  -> kind=date due_on=null recurs=true word=null
✓ one-off + no day refused     -> violates check constraint "audit_findings_date_has_a_date"
✓ recurs null + no day refused -> violates check constraint "audit_findings_date_has_a_date"
✓ date with a day still accepted
```

and the constraint as the database now holds it:

```
$ npx supabase db query --project-ref <staging> --linked \
    "select conname, pg_get_constraintdef(oid) from pg_constraint
      where conrelid='public.audit_findings'::regclass and conname like '%date%';"
  audit_findings_date_has_a_date
  CHECK (((kind <> 'date'::text) OR (due_on IS NOT NULL) OR (recurs IS TRUE)))
```

## 3. The one variable

| Variable | Value | |
|---|---|---|
| `AI_MODEL_AUDIT` | **`claude-opus-5-5`** | What runs an audit. **Set it in the Vercel dashboard BEFORE the push**, so the first deployment of this code already has it. |

**Set it first, and not after.** A variable change is itself a redeploy. Setting it afterwards means
two deployments and a window in between in which audits ran on a model nobody chose — and if a result
moves, nobody can say which of the two changes moved it. (Documents rev 1 did it the other way round
on purpose, for `AI_SCAN_STRUCTURED`, because there the variable was the thing being tested; here it
is the thing being shipped.)

**What happens if it is not set.** `lib/ai.ts` falls back to the judgement tier:
`TASK_MODELS.audit = () => process.env.AI_MODEL_AUDIT || TASK_MODELS.judgement()`. On production
`AI_MODEL_JUDGEMENT` is `claude-opus-5` — see `docs/RELEASE.md`, which is the authoritative record of
what Vercel holds. That is **a different model from the one the rev 1 baseline measured**, and the
dearer one: the documents bake-off priced the two on the same seven documents with no schema at
**$0.5153** a scan for `claude-opus-5` against **$0.2809** for `claude-opus-5-5` (`DECISIONS.md` §139).
So leaving it unset is not "the default"; it is an unmeasured, more expensive model, silently.

**Nothing else changes.** `AI_AUDIT_STRUCTURED` exists and **unset means OFF** — deliberately not the
scan's inverted convention — and it has never been measured against the baseline, so it stays absent.
`DEV_MAX_SEARCHES` is not set on production and must not be. `NOTIFY_TEST_TO` is confirmed absent and
must stay absent: set there, every customer's audit email goes to that address instead of to them.

## 5. What changes for a person on production, the moment it deploys

- **There is an Audits page**, at `/audits`, already in the nav. A box they type into — "Audit us for
  Oregon DEQ", "Audit everything", "Audit us against the attached checklist" — one thin line saying
  how many documents were read, how many agencies and when the last audit was, and then one row per
  agency with its own count, its own date and its own Audit button.
- **An audit arrives by email**, not by waiting. Every finished run is emailed, plain text, the
  summary and a link. There is no batch-of-one silence: one agency is a minute on the cheapest model
  and three on the real one, and an audit that finishes silently is an audit nobody reads.
- **The report opens in the same drawer a document report opens in.** Folded when it has more than one
  section — every section closed with its count, so the shape of the answer is visible before it is
  read. An agency report opens Findings. Every line points at a document, with a page or a condition
  reference and a quote, or says what is not on file. **Four words and no score:** on file, out of
  date, nothing on file, not a document question.
- **They can attach a checklist** — their own monthly form, or their auditor's field form — and get
  one answer per line against the documents on file. A form naming another company is noted and
  audited anyway.
- **They can print the report, make a checklist from it, dismiss a line with a reason, and download
  the documents that audit read as a zip.**
- **The old audits page is gone.** It computed readiness numbers from `document_reviews` and silently
  dropped documents it could not read. Its tables are kept; nothing reads them. A person who had
  bookmarked it gets the new page.
- **No price anywhere.** What a reading cost is in `ai_calls` and in `npm run cost`, and on no
  customer screen.

## 7. Smoke test — to run on the live site, signed in under `CB-Test-3`

**Expect one real-model audit run and about a dollar.** The rev 1 baseline priced an agency audit at
$0.11 for one document and $0.56 for a three-section checklist, on `claude-opus-5-5`; a company with
two or three agencies is in that range per section.

Each step says what passing looks like, so a difference is visible rather than argued about.

1. **Open `/audits`.** Pass: the page loads, the thin line under the box reads "<n> documents read ·
   <n> agencies" and, if there has never been an audit, says nothing about a last one. One row per
   agency, each saying "not audited yet". **No banner anywhere.** Fail: the old readiness page, a
   percentage, or a price.
2. **Type "Audit everything" and send.** Pass: a grey line appears saying it is running, with an
   estimate that either names a measured time or declines to estimate ("This is your first audit; we
   will email you when it is done") — **never a number with nothing behind it**. Fail: a spinner with
   no words, or an instant result.
3. **Wait for the email.** Pass: it arrives, plain text, with the summary and a link, and it is
   addressed to the signed-in person and **not** to a test address. Fail: no email, or an email with
   a price in it.
4. **Open the report from the email's link.** Pass: it opens in the drawer, folded if it has more
   than one section, each section closed with its count. Open Findings: every line points at a
   document with a locator and, where the reading carried one, a quote — or says what is not on
   file. The four words, no score. The sentence about what the report is, outside the folds. **This
   is the step that would reproduce §6's template refusal if it is going to**; on an agency audit it
   would show as a section reading "could not complete" with a reason.
5. **Open Dates.** Pass: a date with no day reads "<title> — recurs, no date in the reading", sits at
   the bottom, and has no "Add to calendar" link. Fail: a blank date, or an invented one.
6. **Print it.** Pass: every section prints, including the folded ones, with the drawer's own header
   and no page furniture. Fail: a printed report with a collapsed section — a report missing a page,
   which nobody reading it on paper can expand.
7. **Download the documents.** Pass: a zip containing exactly the documents that audit read.
